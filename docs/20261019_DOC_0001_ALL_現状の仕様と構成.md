## 2. 時刻の決まり（遊びのルール）

- 作業（タスク）: 名前・所要時間（台所は分、現場は日）・使う資源（1〜2個。0個は「待つだけ」）・前提（先に終わっている必要がある作業）
- 資源（レーン）: 台所は 手・コンロ・炊飯器・オーブン・電子レンジ、現場は 職人・ショベルカー・トラック・生コン車・クレーン。★3 ではコンロ／職人が2つになることがある。待つだけの作業は「待つだけ」のレーンに出る（資源ではないので、いくつでも同時に待てる）
- 置く前に、カードに「いま置くと◯〜◯分」が出る（道具の順番待ちで遅れるとき・前の空きに入らないときは、その理由も）
- プレイヤーは作業カードを1枚ずつタップして順番を決める。前提がまだ置かれていないカードは押せない（「先に〇〇」と出る）
- 置いた順に、開始時刻 = max(前提の作業がすべて終わる時刻, 使う資源それぞれの空く時刻)。レーンの末尾に積み、前に割り込まない
- 同じ種類の資源が2つあるとき（#0005）: 前の作業（同じ種類の道具を使うもの）がまだそのレーンの最後にいれば、そのレーンで続ける（温めた油のコンロで揚げる）。それ以外は、続きを待っていないレーンの早く空いたほう。どれも開始時刻は変わらない
- 全部置いたときの最後の終了時刻が完成時刻。最短なら★3、最短 + 最短の1割（四捨五入、少なくとも1）以内なら★2、それより遅ければ★1（`Engine.grade`）
- この決め方では最適な日程の開始時刻順に並べれば最短に届くので、全部の並べ方を試せば本当の最短が求まる（エンジンはこれで最短を出す。2つある道具の決まりは、早く空いたレーンを残すので、どの並べ方でも完成を遅くせず、最短は変わらない）

## 3. 段取りエンジン（`// ==ENGINE START==`〜`// ==ENGINE END==`）

- グローバル `Engine`。DOM・window・localStorage を使わないので Web Worker でも動く。外への通信なし
- 乱数は seed から決まる mulberry32 だけ。生成は試行の回数で打ち切る（端末の速さで問題が変わらない）
- 現在の `VERSION` は **4**（#0002 で 1 → 2、#0003 で 3、#0005 で 4）

### API

| 関数 | 役割 |
|------|------|
| `generate({ seed, star, theme })` | 練習の問題。star 1〜3、theme `'kitchen'`/`'site'` |
| `daily('YYYY-MM-DD')` / `dailyConfig(...)` | 今日の段取り（No.・曜日つき）／問題を作らずに設定だけ |
| `schedule(pz, order)` | 置いた順（途中でもよい）の日程・完成時刻・各レーンの空き時間 |
| `canPlace(pz, placed, i)` | 置けるか・待っている前提 |
| `solve(pz)` | 最短・最短の並べ方の数・総数・よく知られたコツの完成時刻 |
| `explain(pz, order)` | 「ここがコツ」の1〜2文・最初に分かれた位置（diffAt）・分かれた作業（diffTask）・あなたの頭を引き継いだ最短の一例 |
| `grade(pz, ms)` / `near(best)` | 結果の★（3・2・1）／★2 になる差（最短の1割を四捨五入。少なくとも1） |
| `WEEK` / `SHAPE` | 曜日の★とテーマ／★の形（画面の曜日の表・作業の数はここから作る） |
| `tutorial(1〜3)` / `example()` | はじめての段取り（案内の文 lesson: intro・tip・on・hint・done）／遊び方の例題 |

### 部品表

- 台所: 献立 22（料理の部品 35 から組む。お弁当2つは練習だけ）。現場: 工事の題材 13。作業名は9文字まで、同じ問題の中で重ならない
- 献立の説明と作業を合わせる（#0005）: おにぎりは必ず握る、炊き込みご飯は必ず具を刻む、ピザは「焼きたてのピザ」（生地をのばすだけの形もある）
- 現場の「塗る→乾かす」などのグループは rare（入れる確率 0.3。入れなくても条件を満たせるなら入れない）
- 作業名の決まり: 同じ名前の作業は、どの問題でも同じ資源を使う。クレーンだけで吊る作業は「〜を吊り込む」、クレーンを使う「据える・立てる・架ける・載せる」は職人＋クレーンの作業だけ（#0002）
- 和の朝ごはんでは目玉焼きと卵焼きを同時に出さない（目玉焼きの代わりに焼き魚。#0002）

### ★の形

| ★ | 作業 | 資源の種類 | 2資源同時 | そのほか |
|---|---|---|---|---|
| ★1 | 4〜5個 | 2〜3 | なし | |
| ★2 | 6〜7個 | 3〜4 | 0〜1個 | |
| ★3 | 7〜8個 | 4〜5 | 0〜2個 | 同じ種類が2つ、または2資源同時の作業がある |

### 良い問題の条件（生成でふるいにかける）

1. 最短の並べ方の数 / 前提を満たす並べ方の総数 ≤ **0.2**（★2・★3）。**★1 だけ 0.4 まで緩めている**（目安 0.34。エンジンは目安以下の問題を優先して探す。#0003 で 0.5 → 0.4）
   - 理由: ★1 は作業4〜5個で、並べ方が数通り〜数十通りしかない。資源の違う作業どうしは入れ替えても同じ日程になるので、0.2 ではほとんど作れない。目安 0.34 以下は台所約9割・現場約半分。月・火の日替わりはやさしい日として意図した緩和
2. 画面のカードを上から順に置いたときの完成時刻 ≥ 最短 + 3
3. ★2 以上: よく知られたコツ（長い作業から先に・放置できる作業から先に）だけでは最短に届かない。★3 はさらに「後に続く流れが長い順」でも届かない。同点（所要時間が同じなど）の選び方は全部たどり、どれでも届かないこと（#0003）。「いちばん早く始められる順」でも届かないのは★3 の目安
4. smart（いちばん早く始められる作業の中から1つずつ選んでいくだけで最短に届く確率）が ★2 は 0.5 未満・★3 は 0.3 未満（お弁当の★3 は 0.5 未満）。★3 はできれば 0.15 以下、★2 はできれば 0.15 以上（#0005。★2 が「空いたらすぐ置く」で解けず、★3 が同じ週の★2 よりやさしくならないように）
5. できたての料理（焼く・揚げる・いれる）は、どれか1つの最短の段取りで完成の少し前に仕上がる（お弁当・作り置きは除く。#0003）

### 日替わり

- No. = 2026-10-19 を No.1 とした通し番号（端末のローカル日付）。seed = `dandori-YYYYMMDD`
- 曜日で★とテーマ（#0003。`Engine.WEEK`）: 月 ★1 台所／火 ★1 現場／水 ★2 台所／木 ★2 現場／金 ★2 台所／土 ★3 台所／日 ★3 現場
- 献立・題材は No. ごとに、最後に使ってからいちばん日がたった3つから選ぶ（7日以内に同じものが出ない。お弁当は出さない）。約30年（No.10958）より先は日付の hash で選ぶ（遠い先の時計でも固まらない）
- `dailyConfig` は No.1 より前の日付で No.0 以下を返す。丸めは画面の DAYRULES で、**日付ごと** No.1 の日（2026-10-19）にする（#0002）

- はじめての段取り: 第1話「並べてみよう」（手だけ。どの順でも8分。後から置いた作業は列の後ろにつき、前の空きに入らないことも教える）、第2話「待ち時間を使う」（炊飯器。最短20分）、第3話「取り合いを避ける」（コンロ1口。最短16分）。置くたびに付箋の案内が変わる（最短に届く流れなら lesson.on、外れたら lesson.hint。答えの作業名は言わず、答えは結果の「ここがコツ」で見せる）。最短に届くと次の話へ。記録には数えない
- 練習の途中は1件だけ保存する。完成のあと［もう一度］で並べている途中に離れても、同じ★・テーマを押せば同じ問題の続きから開く（#0005）
- 問題は「読み込み中」を出してから次のフレームで作る（★3 の現場はスマホで 0.3 秒前後かかることがあるため）。Worker は使っていない
- 効果音は WebAudio でその場で作る。振動は navigator.vibrate（画面に触れる前は呼ばない）、iOS アプリは Haptics（置く = 軽い impact・完成 = 中くらいの impact・最短 = success・まだ置けない = warning）。どちらも設定で OFF
- 画面が裏に回ったら（タブを切り替えた・iOS アプリが裏に回った）、並べている途中を保存し、再生・完成の演出・音を止める。戻ったら日付を確かめ、完成の演出の途中なら結果へ（#0006）
- iOS アプリ（Capacitor）との連携は `// ==NATIVE START==`〜`END` の `NATIVE`・`plug`。プラグインは `window.Capacitor.Plugins` から使い、Web では何もしない。使うのは App・Haptics・LocalNotifications・Preferences・StatusBar（詳しくは #0006）
- Service Worker は直接開いたとき（https・ローカル）だけ登録する。iOS アプリ・iframe（Claude Artifact）・sandbox・file: では登録しない。manifest と apple-touch-icon も、iframe・sandbox の中では置かない
- alert / confirm / prompt は使わない。コピーできない環境（Artifact の iframe など）では、結果の文を選択した状態の欄を出す。結果の文の最後には公開 URL（https://kiyotake1229.github.io/dandori-meijin/ ）
- デザイン: 方眼紙の紙面・藍の罫線（ダークは青焼き）・レーンごとの付箋の色・完成時刻の大きな数字。台所は橙、現場は黄のアクセント。書体は Dela Gothic One（見出し）・BIZ UDPGothic（本文）・IBM Plex Mono（数字）。アイコンはすべてインライン SVG。prefers-reduced-motion で動きを止める
- 画面の行き来はブラウザの履歴にも積む（Android の戻るで前の画面へ）。段取り→結果、結果→もう一度・次の問題は履歴を置き換える

## 5. 日付と連続日数（`// ==DAYRULES START==`〜`END`）

- 今日 = 端末のローカル日付。2026-10-19 より前なら日付ごと 2026-10-19 にし、ホームと記録帳に「端末の日付を確かめて」を出す
- 日替わりを **その日のうちに完成させた**（最短でなくてよい）ら連続 +1。夜に開いた段取りは翌朝3時までに完成させれば開いた日の分
- 日付が2日以内で戻っても（時差）連続を巻き戻さない。大きく戻した・進めた時計は、時計のずれとみなして数え直す
- 考え方は嘘つき村（`../index.html`）と同じ

```js
  daily: { 'YYYY-MM-DD': { state: 'playing'|'done', order, guess, asked, tries, bestMs, lastMs, lastOrder, reachedAt, best, v, openedOnDay, solvedOnDay, streak, everBest } },
  practice: { cur: { seed, star, theme, state, ...同じ項目 } | null, solved, perfect, byStar: {1,2,3} },
  tutorial: { done: 0〜3, dismissed, cur: { ep, ... } | null },
  stats: { streak, bestStreak, lastDailyDate, totalSolved, perfect, guessN, guessExact, guessNear, guessErr } }
```

- 読み書きはすべて try。中身は型を確かめてから使う（1件ずつ読み、読めない1件だけ捨てる）
- 壊れた JSON は `dandori.v1.broken` に控えてから空の記録で始める。新しい版の保存（v が2以上）は読まず、上書きもしない
- 記録を変えるときは、保存済みの最新を読み直してから自分の変更だけを重ねる（別のタブの記録を消さない）
- iOS アプリでは保存のたびに Preferences にも同じ JSON を書く。起動時は Preferences を読み終えてから始め（最長1.2秒）、localStorage が空・壊れている・開いたときに空だった、または Preferences のほうが新しければ Preferences から戻す。読み終えるまでは Preferences に書かず、空の記録も保存しない（#0006）
- 「記録を消す」は `epoch` を新しくする。開いていた段取りは開いたときの epoch と違えば途中を書き戻さない。完成させたら新しい記録として数える
- 完成数（totalSolved）= 1回以上完成させた日替わりの日数。最短数（perfect）= 最短に届いた日数。やり直しは何度でもでき、記録は「何回目で最短」と回数
- エンジンの版が変わると同じ日付でも別の問題になる。保存した記録の `v` が今の版と違えば、問題ごとの項目（並べ方・予想・回数・いちばん早い完成・最短に届いた回・最短）を空に戻してから重ねる（`freshForVersion`）。その日のうちに開いた・完成させた・その日の連続と、完成した日の印は残す。前の版で最短に届いた日は `everBest` を付け、最短数を数え直さない（#0005）
